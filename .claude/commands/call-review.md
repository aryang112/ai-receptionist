# /call-review — twice-daily production call QA sweep

Review every production call since the last review for bugs and ungraceful
customer handling. Erica is live on the salon's real number through production
forwarding (whose schedule can change) — this is the standing quality gate.

The cloud `erica-call-qa` routine is a second reviewer, not ground truth. When
its latest email/report is accessible, reconcile every finding below. Do not
repeat an automated claim as fact without independently checking its evidence.

## Data sources
- Admin API: `https://erica-production-f2e2.up.railway.app/admin/api/...`
  Auth: `Authorization: Bearer <ADMIN_TOKEN>` — read the token from `.env`
  (`grep '^ADMIN_TOKEN=' .env`). NEVER print or log the token itself.
- Review state: `data/review-state.json` (local, gitignored) —
  `{ "lastReviewedTs": <ms>, "lastRunISO": "<iso>" }`. If missing, default
  lastReviewedTs to 48h ago.

## Known numbers
- **`fromLast4: "5169"` is Aryan's TEST phone.** Calls from it
  are internal test calls, not customers. Still review them for regressions
  (they often exercise fresh deploys), but exclude them from customer-traffic
  stats, frustration-signal clustering, and "damage" verdicts in the report —
  label them as test calls.

## Procedure
1. Read `data/review-state.json`. Fetch `/admin/api/calls?days=7` and keep
   calls with `startTs > lastReviewedTs`. Report webhook-blocked entries as a
   count only (they worked as designed).
2. For EACH new call, fetch `/admin/api/transcript/<callSid>` and reconstruct
   the dialogue (`entries[]` have `role: 'caller' | 'erica'`). A 404 on a
   call longer than ~20s is itself a finding (transcript persistence gap).
3. Retrieve the most recent `erica-call-qa` email/report when the current
   session has access to it. Map each cloud finding to a call and grade it
   independently as **VERIFIED**, **LIKELY**, **NEEDS LISTEN**, or **FALSE
   POSITIVE**. If the report is inaccessible, say so; do not infer its contents.
   If there are zero new calls, still reconcile any accessible report before
   updating state and finishing.
4. Judge each call against the rubric below. Cross-check factual answers when
   suspicious: hours/closed-dates against `src/config/business.json`, prices
   against the live catalog (`npx tsx scripts/list-services.ts` — read-only).
5. Sweep server logs for the same window:
   `railway logs --service erica 2>&1 | head -300` (note: current container
   only). A WARN/ERROR is a lead: establish caller impact or a violated
   invariant before calling it a product bug. A restart can erase the admin
   endpoint's in-memory log ring.
6. Write the updated `data/review-state.json` (newest reviewed `startTs`).
7. Report, then propose (do NOT auto-apply) fixes for any real bug found.

## Evidence rules
- The transcript is generated by a separate transcription model. It is useful
  for dialogue and intent, but cannot by itself prove clipping, overlap,
  interruption, pauses, exact spoken names/numbers/times, or which side hung
  up. Those claims are always **NEEDS LISTEN** until the recording is checked.
- The call list exposes tool name + `ok`, not arguments or full result details.
  `ok: false` can be an expected safety, closure, availability, or validation
  rejection. Treat it as a lead unless caller impact is independently shown.
- `outcome: "none"` is not automatically a failed booking. Confirm that the
  caller accepted a specific slot and expected a booking; declining options,
  changing their mind, or hanging up before confirmation is not a defect.
- A server log line is evidence that an event occurred, not automatically that
  a caller was harmed. Correlate it to the call and expected fallback behavior.
- When sources conflict, report the conflict and the missing evidence. Never
  pick the more alarming interpretation just to produce a finding.

## Rubric — what "less graceful" looks like
Per call, check:
- **Greeting**: verify the expected words in the transcript; use the recording
  before claiming it was skipped, clipped, or truncated.
- **Listening**: Erica's replies actually answer what the caller just said —
  flag non-sequiturs, ignored corrections ("no, I said…"), repeated
  questions the caller already answered. A transcript turn ending mid-sentence
  is only a reason to listen, not proof Erica talked over or cut the caller off.
- **Accuracy**: hours, open/closed-now, prices, address must match
  business.json / the live catalog. Never-guess rules: flag any invented
  price, service, or availability.
- **Booking integrity**: service + date + time + name confirmed before writing;
  if the caller accepted a slot, verify the resulting appointment rather than
  inferring success/failure from transcript wording or `outcome` alone.
- **Contact/transfer**: Richa's live-transfer window is independently configured
  (default 9 AM–9 PM ET), not the salon's business hours. During an active
  salon closure, the deterministic closure gate suppresses the dial: Erica
  explains Richa is away, asks what the caller needs, handles supported salon
  work directly, and only offers a message after the need is known when it is
  personal/Richa-only/unsupported or the caller requests one. Outside the
  transfer window, offer the message path. Never promise a callback or read
  IDs/URLs aloud.
- **Endings**: no abrupt/mid-task hangups; `endReason` should make sense
  (flag `silence — no response` on a call where the caller was mid-flow,
  `duration cap` on any real conversation).
- **Frustration signals**: repeats, "hello?", sighs, hang-up right after an
  Erica turn, call-backs from the same number within minutes (check for
  same-`fromLast4` clusters).
- **Precomputed flags**: investigate every flag the API already set
  (`tool-error`, `transfer-failed`, `silence-hangup`, `duration-cap`,
  `no-outcome`, `spam`) — a flag is a lead, not a verdict, and expected
  rejections/fallbacks are not defects.
- **Cost sanity**: flag any call whose `estCostUsd` is way out of line for
  its duration (runaway retries).

## Verdicts + report format
Per call: **✅ clean** / **⚠️ minor** (name it) / **🚨 needs a listen**
(say exactly why + note the recording is at `/admin` for that callSid). For
each cloud-QA claim, include its independent disposition: **VERIFIED** /
**LIKELY** / **NEEDS LISTEN** / **FALSE POSITIVE**.
Then a short overall summary: calls reviewed, verdict counts, bookings,
revenue, total est cost, any PATTERN seen across calls (same failure twice =
propose a lessons.md entry and a fix). Lead with the worst finding.

Keep the report tight — Aryan reads this twice a day.
