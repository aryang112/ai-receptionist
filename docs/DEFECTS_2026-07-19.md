## P0 — call-breaking (fix before ANY live testing / deploy)

### TZ-1. Every offered & booked time shifts +4/5h on a UTC server ⭐ worst defect
`src/realtime/twilioStream.ts:678` — availability slots come back from
`phorest.getAvailability` as salon-local ISO **with offset**; the handler
re-parses with `DateTime.fromISO(iso)` (no zone) → formats in the **process
zone**. On the laptop (ET) it works; on Fly/Railway (UTC) a 3:00 PM slot is
spoken as "7:00 PM" and booked at 7:00 PM ET. Reproduced empirically under
`TZ=UTC`. Nothing errors — everything is silently wrong.
**Fix (1 line):** `DateTime.fromISO(iso, { zone: env.TIMEZONE })`. This is the
ONLY unzoned parse in src (all writes/hours/prompt injection are zone-explicit).
Confidence: certain (reproduced).

### RT-1. OpenAI WS clean close is never propagated → zombie call, unlimited silence
`src/realtime/openaiSession.ts:127-145` — `ws.on('close')` stops keepalive,
sets `isConnected=false`, logs… and nothing else. No `onClose` in the handlers
interface; only `error` triggers teardown. If OpenAI closes the socket mid-call
(session limit, service blip), the Twilio leg stays up: audio no-ops, caller
sits in silence forever, objects leak until they hang up.
**Fix:** add `onClose` → same teardown as `onError` (guard on intentional close).
Confidence: certain (verified).

### RT-2. Unconditional `response.create` after every tool result → active-response collision → dropped call
`src/realtime/openaiSession.ts:608` — `sendToolResult` always sends
`response.create`, blind to whether server-VAD already auto-created a response.
**Scenario (the most likely defect to hit in testing):** Erica says "let me
check…", caller interrupts during the tool call, VAD auto-creates a response;
tool resolves → second `response.create` → OpenAI error
`conversation_already_has_active_response` → RT-3 tears the call down.
Also triggered by the prompt's "call suggest_availability for today AND
tomorrow (two calls)" if the model emits both in one response.
**Fix:** track active-response state (`response.created`/`done`); defer the
`response.create` until idle, or specifically swallow that error code.
Confidence: likely (mechanics verified; timing windows need live confirm).

### RT-3. ALL OpenAI error events are fatalized → recoverable glitches drop live calls
`src/realtime/twilioStream.ts:407,1122-1128` — every `error` event routes to
`handleError → cleanup()`. Recoverable errors this code WILL generate:
RT-2's collision, truncate-beyond-audio-length (RT-7/RT-4 interplay),
rate-limit errors. All should be log-and-continue; today each one = click, dead line.
**Fix:** classify by `error.code/type`; only connection/session-fatal errors
escalate. Confidence: certain (routing verified).

### CT-1. Recognized-caller booking is contract-broken: no clientId in book_appointment, no phone anywhere
`src/realtime/twilioStream.ts:192-212` (schema), `:476-481` (prefetch stores NO
phone), `:931-936` (lookup returns NO phone), `src/services/phorest.client.ts`
`getOrCreateClient` (phone-first match, else CREATE).
The injected context orders the model "do NOT ask for their phone number", but
`book_appointment` REQUIRES `customer.phone` and the model was never given it.
Options: ask anyway (violates injection), or fabricate → duplicate Phorest
client / booking on the wrong record (invisible to later "when's my appt?").
Same root breaks: existing client calling from a new number (guaranteed
duplicate), and shared family numbers (books under mom's record no matter
whose name is given — name is silently discarded on phone match).
**Fix:** accept `clientId` in book_appointment (prefer it over phone), thread
the caller-ID phone into `prefetch`, return `phone` from lookup_customer.
Confidence: high (contract break certain; which wrong path the model takes varies).

## P1 — wrong behavior

### PH-1. Client phone index caches a REJECTED promise forever
`phorest.client.ts:283-340` — `clientPhoneIndexLoading` only resets on success.
One failed boot-time load (Phorest blip) → every lookup AND every booking
(`getOrCreateClient → findClientByPhone`) throws for the process lifetime.
**Fix:** reset to null in catch/finally. Confidence: certain.

### PH-2. Already-late callers & same-day cancels can't be found
`phorest.client.ts:866` — `listAppointments` filters `start >= now`. The #1
running-late call ("it's 3:05, my 3:00 appt") returns empty → "I'm not seeing
any appointments" → log_running_late unreachable. Same for post-start cancels.
**Fix:** keep appts whose END ≥ now (or start ≥ now − 2h). Confidence: certain.

### PH-3. Appointments >30 days out are invisible → duplicate-booking offers
`phorest.client.ts:834` — single 30-day window (API caps at 31). Caller booked
5 weeks out → "no upcoming appointments — want me to book?"
**Fix:** page 2-3 sequential 30-day windows. Confidence: certain.

### PH-4. Timed-out POSTs are retried → double bookings / duplicate clients
`phorest.client.ts:208-274` retry loop applies to POST `/booking` + `/client`.
Slow Phorest (>4s) → booked twice; prompt-level retry can make it three.
**Fix:** retry GETs (and read-only availability POST) only. Confidence: certain.

### PH-5. Fuzzy service matcher picks alarming wrong services (verified live)
`booking.ts:32-49` — first-substring-match + numeric-prefix sort order:
"wax" → **"2a) Butt Cheeks Wax"**; "eyebrows" → Permanent-Makeup-Removal $150;
"micro blading" (space) → $0 consult; "massage" → facial add-on standalone.
Erica's read-back confirm is the only safety net.
**Fix:** whole-word + shortest-match preference; return candidates on ambiguity.
Confidence: certain (live-verified).

### CT-2. Multiple same-name matches = unrecoverable dead end
`twilioStream.ts:972-980` returns `{ multiple, count }` with NO candidate data,
but the prompt (:74-75) tells Erica to disambiguate by appointment date/time —
no tool can do that. Likely outcome: fabricated clientId → empty list → tells a
real client they have no appointment. (`lookupCustomerByName` HAS the
candidates; handler discards them.)
**Fix:** return candidate list (clientId + next-appt hint). Confidence: certain.

### RT-4. Barge-in is dead for the buffered tail of every longer answer
`twilioStream.ts:648-651` — `handleResponseComplete` (fires at `response.done`,
i.e. seconds BEFORE playback finishes) wipes `markQueue` +
`responseStartTimestamp`; `handleBargeIn` then early-returns (:631-633) → no
`clear`, no truncate. Interrupting Erica mid-slot-list reliably fails; she
talks over the caller and the next reply queues behind leftover audio.
(OpenAI's reference impl deliberately does NOT reset these at response.done.)
**Fix:** delete both resets (marks drain via 'mark' acks). Confidence: certain.

### RT-5. TPM/rate-limit response failures are silent dead air
`openaiSession.ts:473-497` — `response.done` never checks
`event.response.status === 'failed'`; a rate-limited response logs usage and
"completes". Long call crosses 40k TPM → caller speaks, nothing comes back,
repeat until hangup. **Fix:** detect failed status; retry after
`reset_seconds` (known from rate_limits.updated) or escalate to transfer.
Confidence: certain that detection is absent.

### CT-3. transfer_to_owner tool description CONTRADICTS the prompt
`twilioStream.ts:326` says transfer for "multiple services or group booking…
after one clarifying attempt" — the prompt (:90,:134-140) says multi-service is
normal and transfer is last-resort. Tool descriptions are weighed heavily every
turn → routine two-service bookings may transfer to Richa.
**Fix (1 line):** rewrite the description to match the prompt. Confidence: high.

### CT-4. "Service we don't offer" is a deterministic dead end
Prompt forbids "we don't offer that" (:63) while `suggestSlots` throws
'Service not found' → retry → same error → transfer (or worse: books a
similar-sounding service). No signal distinguishes "unknown service" from
"system failure". **Fix:** return a distinct
`{ notOffered: true, closestMatches }` + prompt guidance ("offer the closest
real service"). Confidence: high.

### CT-5. get_prices miss dumps the full 63-item menu into context
`twilioStream.ts:882-905` — unmatched serviceName falls through to the FULL
catalog: model may read out a list, and the ~1k-token payload lives in context
for the rest of the call, eating the TPM budget the menu was moved out of the
prompt to protect. **Fix:** return top-N closest matches instead of the full
menu; full menu only on explicit "what do you offer". Confidence: high.

### PH-6. Reschedule may fail for long-standing appointments
`phorest.client.ts:550-594` — direct GET /appointment/{id} 404s on this tenant
(always), so `fetchAppointment` scans appointments UPDATED in the last 30 days.
Booked 2 months ago, untouched → not found → reschedule fails → transfer. Also
a mid-call latency smell (guaranteed 404 + up to 10 sequential pages).
Confidence: needs-live-verification (test rescheduling an old booking).

## P2 — cosmetic / edge / latent

- **RT-6** Transfer REST update fires while "let me get Richa—" is still in
  Twilio's buffer → sentence cut mid-word, then Polly voice. Delay update
  ~2s / until marks drain. (`twilioStream.ts:1098-1106`)
- **RT-7** Stray audio deltas after barge-in re-arm truncate state → audio blip
  of the dead sentence; rapid double-interrupt can truncate a cancelled item
  (→ error → RT-3 drops call). Gate deltas on cancelled response id.
- **RT-8** Caller audio during OpenAI handshake (~300-500ms) is dropped, not
  buffered (`twilioStream.ts:573`) — impatient "hello?" gets clipped.
- **RT-9** No callSid tag on any openaiSession log line → two concurrent calls
  interleave transcripts/latency/TPM lines unattributably.
- **CF-1** `business.json` closedDates only has 2025 dates — Erica will book
  Thanksgiving/Christmas 2026. OWNER: give the 2026 list (don't guess).
- **CF-2** `hours.ts` `getOpenClose` = first-open→last-close; a future
  split-hours day would offer lunch-gap slots (latent today).
- **CF-3** today/tomorrow baked at call start — 11:58 PM call books wrong day
  at 12:01 AM (rare).
- **CF-4** `USE_MOCK_PHOREST` defaults to MOCK — a deploy missing the env var
  silently serves fake data. Fail-fast in prod instead.
- **PH-7** Service cache: TTL-expired refresh failure throws instead of serving
  the stale copy it still holds.
- **PH-8** Client-index page failure (post-retry) silently drops that page's
  clients → unrecognized → duplicate profiles on booking.
- **PH-9** Exact-match name lookup (no fuzzy): "Priya" transcribed "Prya" → no
  match → duplicate profile at booking.
- **PH-10** Reschedule recomputes end from CATALOG duration — front-desk-
  extended appointments silently shrink on reschedule.
- **PH-11** Cancel-retry semantics for already-cancelled appts unverified — a
  lost success response + retry may report failure for a cancelled appt.
- **CT-6** Two competing verbatim first-line greetings (prompt :50 vs injection
  :496) — occasional blended/double greetings.
- **CT-7** Recognized caller volunteering a NEW number → real lookup misses →
  `{found:false}` contradicts the injection ("existing client on file").
  Also: firstName-without-lastName search silently returns not-found (:955).
- **CT-8** Tool schema REQUIRES phone but `BookSchema` (booking.ts:16) has it
  optional — phone-refusers force the model to fabricate; `sanitisePhone`
  accepts any digit count → junk records under wrong index keys.
- **CT-9** Doc-rot: `phorest.types.ts:27-28` claims start/endTimeRaw are UTC —
  they're salon-local. Exactly how the next tz bug ships. Also `CORE_SERVICES`
  (`twilioStream.ts:31-33`) is dead code that would render IDs, not names.
- **CT-10** "Offer BOTH today and tomorrow" has no carve-out when the caller
  already named a day → two off-target tool calls before checking Friday.
