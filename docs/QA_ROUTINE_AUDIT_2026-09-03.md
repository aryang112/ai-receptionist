# Erica cloud QA routine audit — 2026-09-03

## Bottom line

The twice-daily scheduler has proven that it can run autonomously and send an
email. The weak point is the evaluator contract, not the basic scheduler. The
current routine can miss a call, duplicate a review, and elevate ambiguous
transcript/tool/log signals into findings that the available evidence cannot
support.

Current live enabled/last-run/next-run status remains unverified: the available
Claude browser session was signed out during this audit. Historical execution
is confirmed; current health must not be inferred from that history.

## Wiring reviewed

- Existing routine: `erica-call-qa` (update this routine; do not create another).
- Schedule: `37 2,12 * * *` UTC, with isolated cloud sessions.
- Inputs: protected `/admin/api/calls`, per-call transcript, and `/admin/api/logs`.
- Output: one Gmail report per run, including an all-clear report.
- Local counterpart: `.claude/commands/call-review.md` with a durable local
  `data/review-state.json` cursor and Railway log access.

## Confirmed defects and risks

### 1. Coverage is not complete

The run intervals alternate between 10 and 14 hours. A 13-hour lookback leaves
a one-hour gap across the 14-hour interval and creates a three-hour overlap
across the 10-hour interval. Because sessions are isolated and have no durable
cursor, overlap can also produce repeat findings.

Minimum safe correction: use a 15-hour window and explicitly tolerate overlap.
Robust correction: give the reviewer a durable server-side review cursor/ledger
or another idempotent way to mark call SIDs reviewed. A longer lookback alone
prevents misses but does not prevent duplicates.

### 2. The transfer rubric is stale

Production transfer behavior is not based on salon opening hours. Richa's
personal transfer window defaults to 9 AM–9 PM ET every day. During an active
configured salon closure, a stronger gate suppresses dialing and the expected
conversation is: explain that Richa is away, ask what the caller needs, handle
supported salon work directly, then offer a message only when the discovered
need is Richa-only/unsupported or the caller asks to leave one.

The cloud prompt's older “outside business hours → message” rule can therefore
mark correct calls wrong and miss incorrect closure behavior.

### 3. Several claimed findings exceed the evidence

The persisted transcript is generated by a separate model. It cannot establish
audio timing, clipping, interruption, pauses, exact spoken numbers/names, or who
hung up. Those are listening candidates, not confirmed failures.

The call-list endpoint exposes tool name and `ok`, but not arguments or full
results. `ok: false` may be an expected closure, safety, availability, or
validation rejection. The reviewer cannot call every false tool result a bug.

Likewise, `outcome: none` after a booking question is not proof of a lost
booking. The caller may have declined the choices, changed their mind, or left
before confirming. A booking defect requires evidence that the caller accepted
a slot and the expected write did not occur or produced the wrong appointment.

### 4. Log evidence is useful but incomplete

`/admin/api/logs` is an in-memory WARN+ ring for the current container. A restart
empties it and removes visibility into the replaced container. WARN/ERROR also
does not automatically mean customer damage; expected provider failures may be
handled correctly. Correlate each line to a call and the fallback heard by the
caller before raising it as a product issue.

### 5. Embedded business truth can drift

Hours, closure dates, and address copied into a cloud prompt can become stale.
The authoritative source is `src/config/business.json`; transfer-window values
are runtime configuration. The cloud routine currently lacks a versioned,
sanitized endpoint that reports this QA context, so its rubric must be manually
kept synchronized until such an endpoint is deliberately designed.

### 6. Secret handling is operationally fragile

The read-only admin credential is embedded in the routine prompt because the
routine has no secrets store. It must never appear in reports or logs. Rotation
is a coordinated change across Railway, local configuration, and the existing
routine; changing only one breaks QA access.

## Required reviewer policy

Every automated claim receives one disposition:

- **VERIFIED** — direct evidence establishes the behavior and impact.
- **LIKELY** — evidence is consistent and material, but one non-audio fact is
  unavailable.
- **NEEDS LISTEN** — the claim depends on audio timing/content or transcript
  ambiguity.
- **FALSE POSITIVE** — expected behavior or stronger evidence disproves it.

The local daily review must inspect the latest available cloud QA email, map its
claims to calls, and independently assign these dispositions. No production fix
should be made from the automated report alone.

## Recommended live-routine update

1. Change the lookback from 13 to 15 hours and deduplicate call SIDs within a
   run; label overlap as expected.
2. Replace the business-hours transfer rule with the current independent
   transfer-window and active-closure policy.
3. Apply the evidence dispositions above. Force timing/interruption/exact-word
   claims to `NEEDS LISTEN` because the cloud routine has no recording tool.
4. Treat `tools[].ok === false`, flags, `outcome: none`, and logs as leads that
   require caller-impact evidence.
5. Separate internal tests, clients, and non-client sales/vendor/job/spam calls
   in traffic and damage totals.
6. State the policy/config version or fetch a future sanitized QA-context
   endpoint so stale copied facts are detectable.
7. Preserve the one-email-per-run health signal and make API authentication or
   reachability failure the only automatic critical infrastructure finding.

Updating the existing live routine requires signing into the Claude Code
routines page and explicit approval at the moment of the change because the
routine contains a sensitive credential and controls an external automation.
